# Resuming a subject, and steers after the go-ahead

## Resuming ("continue on <ticket/topic>")

Rebuild state from evidence before round 1: search past sessions for the identifier, re-read the tracker item (comments, link graph, status), and check the worktree (`git status`, branch vs the default branch, grep the code for the symbols the ticket names). Tracker text goes stale after merges and closed siblings, so open with a short "what is already true" list and ask only what that leaves open.

- **Uncommitted WIP from a prior session is a claim, not evidence.** Trace every field it reads back to the type that produces it: an access nothing sets compiles clean behind a cast and silently takes the fallback branch forever. Such a hole is usually a scope question in disguise (the data the acceptance criteria need sits behind a layer declared out of scope); put it as a round-1 question with options — extend the shared layer additively, drop the requirement, or bypass the layer and lose its guarantees. Flag comments that contradict their code and parameters the body ignores: both mark intent never implemented.
- **Settle conflicting tracker text from the generated artifact**, not the newest timestamp — a "correction" comment can be the stale one. When a comment and the description disagree on a wire detail, read the spec, generated client, or route table, and say in the "already true" list which text the artifact confirms.
- **On a wire-detail mismatch between repo convention and the server's published contract, the server's spec is the starting fact.** If the user owns both sides and chooses to change the server, price it with the blast radius at the read sites (handlers, spec declarations, tests) and a survey of every real caller, including unmerged branches (`git grep <name> origin/<branch>`); the caller survey usually decides it. Cite standards only after that survey. Correct and confirm any typo in a name the user dictates — a misspelled header matches nothing.

## Steers after the go-ahead

- A mid-implementation message that changes a settled decision (drops a mechanism, moves a trust boundary, widens scope) re-opens the frontier. Read the code that decision touches, say what it removes and what depends on it, and ask the new questions with recommendations: how far it goes, which change/MR carries it, what happens meanwhile, what the interim config must keep so nothing locks out. Keep going only on parts the steer does not touch; tracker write-backs wait for the answers.
- Once answered, search the tracker for an existing ticket for the new work before creating one, then create it linked to the parent. The in-flight change keeps its scope and records the dependency: finish it with the interim config unchanged and record the new work as a row in its review notes.
- "Make X consistent with Y" is not one decision. Decompose it into the layers that would have to match — the rule or credential, the reachability of the capability, the deploy wiring — price each, and ask which are in scope; a rule-only change can leave the capability uniform on paper and unreachable in practice. Verify reachability from the code that generates or registers the surface, not from the symmetry of the two call sites.
- "Deepen and simplify before implementation": read the code the plan touches first (real constructors, wiring sites, generated files, gates) and let it overturn the plan's shape. The deepened task names the outside judge (tests, gates, the live check); the simplify table lists each cut with the requirement that dies. Show both before writing code.
